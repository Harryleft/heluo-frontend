# 答辩演示持久缓存方案（无 UI 标注）

## 1. 背景与目标

当前系统已经具备进程内缓存（内存 Map），但页面刷新、浏览器重启或前端进程重启后缓存会失效。
在硕士答辩演示场景下，主要风险是现场网络波动、后端短时抖动、向量链路瞬时不可用，导致页面出现空态或加载失败。

本方案目标：
- 提升答辩现场稳定性与可演示性；
- 不改变当前 UI 展示文案（不增加“缓存结果”提示）；
- 以最小改动引入可持久缓存能力；
- 保持“数据可控过期”，避免长期陈旧数据。

## 2. 适用范围（仅缓存关键数据）

仅对以下高价值、演示敏感接口启用持久缓存：

1. 详情页推荐资源（`/api/v1/search`，`mode=vector|keyword`，用于推荐资源卡片）
2. 诗文详情（`/api/v1/poems/:id`）

说明：
- 人物 AI 介绍、诗文 AI 赏析暂不做持久缓存，避免答辩中出现“旧生成文本”争议；
- 普通列表页不纳入本次范围，控制改动面。

## 3. 缓存介质与生命周期

### 3.1 介质选择

采用 `localStorage` 作为浏览器持久缓存介质：
- 优点：实现简单、兼容性高、无需引入 Service Worker；
- 风险：容量有限（一般 5MB 左右），需严格控制条目大小和数量。

### 3.2 TTL（过期策略）

建议 TTL：
- 推荐资源缓存：30 分钟
- 诗文详情缓存：60 分钟

原因：
- 兼顾答辩稳定性与数据时效；
- 即使答辩前预热，现场也可覆盖完整演示窗口。

### 3.3 版本化失效

引入 `CACHE_VERSION` 常量（例如 `v1`）：
- 缓存 key 必须包含版本号；
- 若接口结构变更或演示前需强制刷新，仅需升级版本号。

## 4. 缓存键设计

建议键结构：

- 推荐资源：`heluo:cache:v1:related:{uri}:{query}:{mode}:{type}:{page}:{pageSize}`
- 诗文详情：`heluo:cache:v1:poem:{id}:{format}`

键设计原则：
- 与请求参数一一对应，避免错读；
- 避免使用不稳定字段（如随机 requestId）；
- 对 query 与 uri 做标准化（trim、lowercase、编码）。

## 5. 数据结构设计

`localStorage` value 统一 JSON 结构：

```json
{
  "version": "v1",
  "createdAt": 1700000000000,
  "expiresAt": 1700003600000,
  "payload": { }
}
```

要求：
- `payload` 存接口成功响应中的 `data` 核心字段；
- 不存大体积冗余字段（如过长调试数据）；
- 严禁写入用户隐私敏感信息。

## 6. 读取与写入流程

### 6.1 读取流程

1. 生成缓存 key；
2. 读取 `localStorage`；
3. 解析 JSON 失败则删除坏数据；
4. 校验 `version` 与 `expiresAt`；
5. 命中则返回缓存结果；
6. 未命中则走网络请求。

### 6.2 写入流程

1. 网络请求成功后构造缓存对象；
2. 写入 `localStorage`；
3. 若配额异常（QuotaExceeded），触发清理策略后重试一次；
4. 仍失败则降级为“无持久缓存”，不影响主流程。

## 7. 清理策略

建议采用“启动轻清理 + 写入失败清理”双策略：

1. 启动轻清理
- 应用启动或详情页首屏时，扫描 `heluo:cache:v1:*`；
- 删除过期条目；
- 控制最大条目数（如 150）。

2. 写入失败清理
- 遇到 QuotaExceeded 时，按 `createdAt` 删除最老条目；
- 删除后重试写入 1 次；
- 再失败则放弃持久写入。

## 8. 失败降级策略

必须保证“缓存模块故障不影响业务主流程”：

- 读缓存异常：记录 warn，走网络请求；
- 写缓存异常：记录 warn，不中断返回；
- 清理异常：记录 warn，不抛出到 UI 层。

## 9. 与现有缓存体系的关系

当前已有两层内存缓存：

1. `OverviewTab` 页面级 `relatedCacheRef`（组件生命周期内）
2. `v1Api` 级 `relatedResourceCache`（进程内 TTL Map）

新增持久缓存后建议层次：

1. 页面级内存缓存（最快）
2. 进程内缓存（次快）
3. 浏览器持久缓存（兜底）
4. 网络请求（最终来源）

该顺序能兼顾性能与稳定性。

## 10. 答辩前操作建议（演练清单）

1. 答辩前一天：完成全链路联调并执行一次预热访问；
2. 答辩当天：
   - 启动前后端与 embedding 服务；
   - 打开关键演示页面完成首轮缓存预热；
   - 检查 `vector/status` 与 `health` 接口；
3. 若需强制刷新数据：修改 `CACHE_VERSION` 或手动清理 `localStorage` 对应键。

## 11. 验收标准

满足以下条件视为方案达标：

1. 断开后端短时重连期间，推荐资源与诗文详情可从持久缓存回显；
2. 页面不新增缓存标注文案，UI 行为保持不变；
3. 数据在 TTL 过期后自动回源更新；
4. 缓存读写异常不会导致页面报错或白屏。

## 12. 实施边界

本方案仅用于答辩演示稳态增强，不等于长期离线架构。
答辩后如进入生产化阶段，建议升级为：
- 基于 IndexedDB 的结构化缓存；
- 更完善的缓存一致性策略；
- 结合服务端 ETag/Last-Modified 的协商缓存机制。
