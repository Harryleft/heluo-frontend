# Fusion 向量链路提速方案（P0 + P1 + P2）

## 背景

- 当前首页融合问答在 `hybrid/vector` 下，`poem` 召回存在明显超时。
- 已确认向量数据目录存在且有数据，不是路径缺失问题。
- 主要瓶颈集中在：
  - 候选池过大（默认 120）
  - 候选文档处理串行
  - 对大量候选执行“诗词详情/全文补查”
  - 上层作用域超时较紧（默认 9s）

## 目标

- P0：先止血，减少超时概率。
- P1：重构慢路径，降低单请求处理时延。
- P2：引入缓存降低重复请求成本。

## 现状链路

```mermaid
flowchart TD
    A[融合流式请求] --> B[每个 scope 多 query 变体检索]
    B --> C[poem 向量检索]
    C --> D[拉取大量候选文档]
    D --> E[逐条算相似度 + 逐条补查详情/全文]
    E --> F{是否超过作用域超时}
    F -- 是 --> G[poem 分支失败/丢弃]
    F -- 否 --> H[进入重排输出]
    G --> I[最终证据偏向 book/person]
```

## 方案设计

```mermaid
flowchart TD
    A[P0 参数收敛] --> B[作用域超时默认上调]
    A --> C[poem 向量候选池默认下调]
    D[P1 两阶段检索] --> E[阶段1: 并发取文档并算相似度]
    E --> F[先选 TopN 粗排]
    F --> G[阶段2: 仅对 TopN 做详情/全文补查]
    H[P2 缓存] --> I[文档 JSON 缓存]
    H --> J[poem 详情缓存]
    H --> K[poem 全文缓存]
    B --> L[整体超时率下降]
    C --> L
    G --> L
    I --> L
    J --> L
    K --> L
```

## 边界与风险

- 缓存需要 TTL + 容量上限，避免内存膨胀。
- 两阶段 TopN 太小会影响召回质量，需可配置。
- 并发度过高会反向压垮 MarkLogic，需要限流上限。
- 默认超时上调会增加尾延迟，但可换取可用性。
