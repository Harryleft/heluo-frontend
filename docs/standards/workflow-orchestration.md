# 工作流编排

从 CLAUDE.md 提取的详细工作流规范。本文档定义了智能体开发的核心工作流程。

---

## 1. 默认计划模式

- 针对任何非微小任务（3个以上步骤或架构决策），进入计划模式。
- 如果情况出现偏差，立即停止并重新计划——不要盲目推进。
- 将计划模式用于验证步骤，而不仅仅是用于构建。
- 提前编写详细的规范以减少歧义。

## 2. 子代理策略

- 充分使用子代理，以保持主上下文窗口的整洁。
- 将研究、探索和并行分析卸载给子代理。
- 对于复杂问题，通过子代理投入更多计算资源。
- 每个子代理执行一项任务，以确保专注执行。

## 3. 自我改进循环

- 在收到用户的任何纠正后：将该模式更新至 `tasks/lessons.md`。
- 为自己编写防止犯同类错误的规则。
- 严格迭代这些教训，直到错误率下降。
- 在会话开始时复习相关项目的教训。

## 4. 完成前验证

- 在证明其有效之前，绝不将任务标记为完成。
- 在相关时，对比主分支与你的更改之间的行为差异。
- 问自己："主任工程师会批准这个吗？"
- 运行测试，利用 google devtools MVP 检查前端控制台，检查日志，证明正确性。

## 5. 要求优雅（保持平衡）

- 针对非微小更改：暂停并提问"有更优雅的方法吗？"
- 如果修复感觉像是拼凑的："基于我现在所知的一切，实现那个优雅的解决方案。"
- 对于简单、明显的修复跳过此步——不要过度工程。
- 在展示你的工作之前先质疑它。

## 6. 自主修复缺陷

- 当收到缺陷报告时：直接修复它。不要要求手把手指导。
- 指出日志、错误、失败的测试——然后解决它们。
- 要求用户零上下文切换。
- 在未被告知如何操作的情况下，去修复失败的 CI 测试。

## 任务管理

1. **计划优先**：将带有可检查项的计划写入 `tasks/todo.md`。
2. **验证计划**：在开始实现之前进行检查。
3. **跟踪进度**：边做边将项目标记为完成。
4. **解释更改**：在每个步骤提供高层次的总结。
5. **记录结果**：在 `tasks/todo.md` 中添加审查部分。
6. **捕获教训**：在纠正后更新 `tasks/lessons.md`。

## 核心原则

- **简单优先**：使每次更改尽可能简单。影响最少的代码。
- **拒绝懒惰**：寻找根本原因。没有临时修复。遵循高级开发人员标准。
- **最小影响**：更改只应触及必要的部分。避免引入缺陷。
- 高内聚，低耦合
- "快速迭代+持续修正"，而非"一次做对"
- 在提交的反馈信息中需要引用具体文件和行号
